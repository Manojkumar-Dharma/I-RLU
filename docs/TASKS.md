# I-RLU Task Board — for parallel sessions

This project is being built across multiple Claude sessions running in
parallel. To avoid collisions, **claim a batch before starting** (edit the
Status column below in the same commit as your first change) and keep each
batch's changes reasonably self-contained. If you're picking this up fresh,
read in this order:

1. `README.md` — project overview, current status.
2. `docs/REQUIREMENTS.md` — architecture and confirmed decisions.
3. `docs/KEYWORD-INVENTORY.md` — the full DDS keyword inventory this task
   board is scoped against, gathered from RLU's own screens + IBM's DDS
   reference.
4. This file — pick an unclaimed batch, or continue one marked
   "in progress" if you're resuming your own prior work.
5. `docs/ROADMAP.md` — tick off completed items there when you finish a batch.

**Before your first commit in a session**, set the git identity for this
repo (not global) so commits attribute correctly regardless of which
session/environment made them:

```
git config user.name "Manojkumar-dharma"
git config user.email "manojkumar.dharmalingam@gmail.com"
```


## How the codebase is organized (so batches don't collide)

| Area | File(s) | Touched by |
|---|---|---|
| Data model | `src/prtfModel.ts` | Rarely — model is already generic (keyword name + positional params). Only touch if a batch needs a genuinely new model concept (e.g. Batch B's literal-vs-P-field toggle may need a small model addition). |
| Parsing | `src/prtfParser.ts` | Same as above — rarely, unless a batch finds a real DDS construct the parser mishandles. |
| Writing | `src/prtfWriter.js` | Same. |
| Layout/rendering logic | `src/prtfEngine.js` | Most batches that add rendering (C, D, E, I). |
| Webview UI (properties panel, pickers) | `media/webviewClient.js`, `src/buildWebviewTemplate.js` | Most batches that add UI (A, B, C, F, G, H). |
| AFP font metrics | `src/afpFontMetrics.js` | Batch L only. |
| Extension host / compile command | `src/extension.ts` | Batch J for the compile-command work; Batch F added generic `setRecordKeyword`/`removeRecordKeyword` edit kinds here that A/B/G should reuse rather than adding parallel bespoke edit-kind handlers — check `applyEdit` before inventing a new one. |
| Tests | `test/` | Every batch adds its own test file(s) — don't edit another batch's test file. |

**To minimize merge conflicts across parallel sessions**, prefer adding new
functions/sections over editing shared dispatch code. If your batch needs to
add a case to a shared switch/dispatch (e.g. a keyword-name switch in the
engine or webview), add it as a narrow, additive change and say so plainly in
the commit message.

### Batch PP — Bug fix: keyword regeneration disturbed unrelated, untouched physical lines [DONE]
- Flagged directly by Manoj: editing or adding one keyword changed lines that had nothing to do with the edit. - Checked I-SDA's own `dspfWriter.js` for the equivalent problem in display files: it's architected completely differently (targeted line-array splice per field, re-parsing after each edit, never a whole-file regenerate — "so unrelated lines/fields are never touched" is a stated design goal there). Adopting that architecture wholesale would be a much larger rewrite than this batch's scope (I-RLU's `applyTrackedDocumentEdit` always replaces the full document via one `WorkspaceEdit`, and every edit already re-parses the model, per `src/extension.ts`) — instead, this batch brings the SAME "leave what wasn't touched alone" principle to I-RLU's own whole-model-regenerate architecture, one level deeper: down to individual keyword-bearing physical lines within a changed entry, not just entries as a whole.
- **Verbatim-first reproduction**: `emitGroupKeywordLines` compares each conditions-group's original continuation-run text (reconstructed from `ParsedSource.rawLines` via new `originalRunRange`/`originalRunKeywordText`, mirroring `prtfParser.ts`'s own `keywordAreaOf` column/continuation-character conventions exactly) against the CURRENT keyword set's raw text for that run. An exact match (nothing added, edited, or removed) means those original physical lines are spliced back byte-for-byte — this is what makes an untouched entry, or an untouched run within a touched entry, reproduce identically instead of being silently reflowed. A mismatch (including a sibling keyword having been removed, which shortens the current text and correctly fails the comparison) falls through to a fresh repack of only that content.
- **Line-preserving repack fallback**: new `packKeywordsPreservingLines` packs using each keyword's own `raw` text as an atomic unit — never rejoining into one string and re-tokenizing by whitespace, which is what `emitWithKeywords`'s existing `tokenizeKeywordText` does and would incorrectly split a multi-parameter keyword like `LINE`/`BOX`/`FNTCHRSET` mid-parameter if a wrap point fell inside it (a real, separate latent bug found and fixed along the way — confirmed by reproducing it against real hand-authored source in `test/fixtures/sample-afpds.pf`, where `PAGSEG(COMPLOGO 0.5 0.5)` legitimately wraps mid-keyword under the OLD writer). The one necessary exception: if a SINGLE keyword's own full text is longer than the column width by itself, there is no way to fit it on one physical line at all, so (and only then) it falls back to the same quote-aware whitespace sub-splitting `tokenizeKeywordText` already does.

- Key files: `src/prtfWriter.js` (`emitGroupKeywordLines`, `packKeywordsPreservingLines`, `originalRunRange`, `originalRunKeywordText`, `splitIntoSourceLineRuns`; `emitEntryWithConditionedKeywords` now threads `ParsedSource.rawLines` through from all four `regenerateSource` call sites), `test/prtfBatchPP.test.ts` (13 new tests: adding/editing a keyword leaves sibling entries byte-identical, a mid-keyword-wrapped `PAGSEG` entry round-trips exactly when untouched, editing one keyword among several sharing an original line only reflows that group, a freshly-added long `FNTCHRSET` wraps safely with no truncation, a freshly-added `LINE` is never split mid-parameter, the literal-before-keyword ordering case, plus direct unit tests for `packKeywordsPreservingLines`/`originalRunRange`/`originalRunKeywordText`). `emitWithKeywords`/`tokenizeKeywordText`/`keywordsToText` are left completely unchanged (still exported, still used by their own existing tests) — only the two production call sites inside `emitEntryWithConditionedKeywords` were rewired to the new functions.
